Release Orchestrator

A strong Cursor MCP that runs your weekly release in one place — tickets through Word notes, SharePoint, change ticket, and Slack — in about 5–15 minutes when tickets are ready. You preview first; nothing sends until you say so.

Goal

Build one internal release assistant — Release Orchestrator MCP — so BI and engineering teams can prepare a production release, create change tickets, publish notes, and notify the right people without repeating the same manual Jira and document work every week.

Description

Standardize how releases are prepared: pull tickets from Jira, group them by report, write internal release notes and client-facing notes, upload files to SharePoint, create the change ticket with plans and approvers, post the deploy message in Slack with the correct ticket link, and send Outlook or Slack messages to owners, testers, and leadership. Everything uses the same ticket list so nothing drifts apart.

Success looks like

  • Any supported release can be prepared and reviewed in one guided flow in Cursor.
  • Change tickets are created with validated fields and a preview before submit.
  • Release notes and client notes are generated from Jira, not rebuilt by hand.
  • SharePoint, the change ticket, and Slack all point to the same version and files.
  • New release owners can walk through the guide with the team in 5–10 minutes and run the full path the same day.

What we achieve

  • One consistent process instead of ad-hoc updates in Jira, Word, chat, and email.
  • Fewer missed fields, duplicate report lines, and wrong links in deploy messages.
  • A clear trail of who deployed what and when.

What we use it for

  • Weekly dashboard and report releases (standard and custom clients).
  • Creating change tickets for production deploys.
  • Word release notes for stakeholders and shorter client notes where needed.
  • Slack deploy announcements, Outlook mail, and Teams meeting reminders.
  • Picking safe deploy dates around weekends and company holidays.

What problem it solves

Before

Tickets in Jira, notes in Word, folders hunted in SharePoint, change ticket filled field by field, “please comment” in group chats, deploy post with the wrong link. Same report listed three times. Easy to miss a tester or a holiday.

With the MCP

One list drives notes, files, change ticket, and messages. Developers answer on the Jira ticket only. You preview Slack and mail, then send. Deploy dates skip Fridays and bad holiday gaps.

You stay in control — preview first, confirm every live send.

How fast it is

When tickets already have the right Jira comments, the MCP runs the full path in one session — load tickets, notes, SharePoint, change ticket, Slack, and Outlook previews — in about 5–15 minutes. Manual work used to spread across half a day.

Simple flow (every release)

flowchart TD A["Setup in Cursor"] --> B["Pick version and program"] B --> C["Review tickets in Jira"] C --> D["Teams review call"] D --> E["Release notes + client notes"] E --> F["SharePoint upload"] F --> G["Create change ticket"] G --> H["Slack deploy post"] H --> I["Outlook and Slack to team"] I --> J["Production deploy when ready"]

Leadership gets notified when the change ticket exists. Assignees get a Jira reminder on their tickets. Deploy only on a safe workday (not Friday).

Quick onboarding (new users)

  1. Open the Release Orchestrator repo in Cursor.
  2. Say Setup Release Orchestrator and sign in to Jira, Slack, and Outlook when asked (once).
  3. Reload the MCP in Cursor.
  4. Start a release: choose program (Glofox or Ignite), pick versions, follow the steps in order.
  5. Always preview Slack and email before sending live.
